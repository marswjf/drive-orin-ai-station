  |---|---|---|---|
  | 基线 | 27.43 GiB | 27.42 GiB | 0.01 |
  | 占 4 GiB | 23.47 | 23.47 | 0.00 |
  | 占 8 GiB | 19.50 | 19.48 | 0.02 |

  一比一跟随。所以**"显存 23.77 GiB"是错误表述**——那只是第一轮测量时刻系统恰好可用 24.6 GiB 的结果（实验②的 23.47 几乎复现了它）。Orin 统一内存架构下 GPU 和 CPU 共用同一块物理内存，真正固定预留给 GPU 的只有 nvmap carveout：`generic-0` 1 GiB（实测全空闲）+ `fsi` 16 MiB。

- **被 isolcpus 隔离的 CPU5 不能用于推理，强行用会让性能崩 6 倍**【llama-bench 实测，反直觉】：

  | 配置 | tg32 |
  |---|---|
  | 不绑核，10 线程 | 10.09 t/s |
  | 不绑核，12 线程 | **4.79 t/s**（线程数 > 可调度核数，同步屏障被拖垮）|
  | `taskset -c 0-11`，12 线程（含 CPU5） | **1.67 t/s** ← 最差 |
  | `taskset -c 0-4,6-11`，11 线程（避开 CPU5） | **10.54 t/s** ← 最优 |

  机理：`isolcpus` 把 CPU5 移出调度器负载均衡（`taskset` 仍能绑上去，实测绑定成功且确实运行在 CPU5），但在 PREEMPT_RT 内核下该核的调度/中断语义不同；llama.cpp 是**同步屏障式并行**，任何一个线程慢，全体等它。所以"解锁隔离核拿回算力"这个直觉是错的——**正确做法是反过来显式绑核避开它**。这也解释了为什么线程数设成 12 会断崖式掉速。

- **面板代理曾不传播客户端断开，实测对照确凿**：同样发长请求后强行断连，**直连 8080 → slot 立刻 `is_processing=false`；经面板 9000 → 25 秒后仍 `true`**。修复（`bindUpstream` 在 `res` 的 `close`/`aborted` 时 `p.destroy()`）后再测，经面板也立即释放。这解释了 WeKnora 报 `client_gone / context canceled` 之后板子仍 99% 满载、后续请求全部排队卡住。
- **长 prompt 处理时间线性可算**【实测】：WeKnora 单请求 68,911 token 输入，NewAPI 记录 FRT 1m55s；按实测 prompt 655 tok/s 算 68911÷655≈105 秒，**吻合**。所以这类"卡住"先算一下就知道是不是物理下限，不必当故障查。
- **`parallel=1` 是长上下文的必要条件**：KV 按 `n_ctx` 总量分配，`parallel=2` 会把 128K 切成两个 64K，而 68,911 token 的请求超过 65,536 就装不下。**不能靠加并发解决排队问题。**
- **`-nothink` 模型名变体**【实测】：面板在转发时识别 `-nothink` 后缀 → 还原真名 + 注入 `enable_thinking:false`。同一问题 `qwen3.6-35b-a3b` 12.9s（思考 1220 字）vs `qwen3.6-35b-a3b-nothink` **1.6s**。上游只有一个模型实例，不额外占内存。`/v1/models` 会列出这个变体，网关同步模型列表时自动带上。
- **局域网网关转发板子模型完全正常**【实测】：`/v1/models` 列得出、非流式 200、流式增量正常、工具调用 `finish_reason=tool_calls` 参数正确。用户报的"跑不通"是思考模式造成的表象，不是链路故障。
- **模型自述"运行在阿里云分布式集群"**：训练数据里的自我认知，与实际硬件无关，不影响功能。别拿模型的自述当环境事实。

## 【B 多轮才站住】

- **平台身份**：第一反应按 Jetson AGX Orin 处理，头两轮 smart-search 都按 Jetson 检索（"jetson_clocks/nvpmodel/改DTB carveout"），结论基本不适用本平台。读到 `dt-model=p3663-XXXX` + `root=/dev/vblkdev0` + `tegra_hv` 才定性为 DRIVE OS Guest，检索重做。→ 教训：**型号先从板上读，别从"长得像"推**。
- **4.1G used 归因**：报告初版写"37×tzvault + fsicom + containerd… 占 4.1G"，按 `ps` 的 RSS 类别列的，没做 PSS 核算。后来逐进程 `smaps_rollup` 实测发现用户态总 PSS 仅 ~200MB，4.1G 里约 3.9G 是内核级预留（进程停光也拿不回）。→ 教训：**内存归因别信 RSS 类别相加（共享页重复计数），要用 PSS；"used 高"不等于"进程占得多"**。
- **空载 67°C 的成因**：初判倾向"热量堆在 SoC 散不出、散热路径问题"。查 `scaling_governor`（performance 锁频）+ `disable_power_features` + GPU railgate 全关后，确认空载高温主因是**主动关掉了所有省电**，67°C 是"什么都不干"的地板。→ 但注意这是"地板成因"的修正，**不构成"散热够用"的结论**——加载后会不会过热仍属 C 档未测。
- **"板上没有 libcuda.so"（第一轮结论，错的）**：第一轮只查了 `/usr/lib/aarch64-linux-gnu/libcuda*` 和 `/usr/lib/aarch64-linux-gnu/tegra/`，两处都没有，就写成"没有 libcuda，CUDA 程序跑不起来"。第二轮用 `ldconfig -p` + 全盘 `find` 才发现它在 `/usr/lib/libcuda.so.1`。→ 教训：**又一次栽在 Jetson 路径习惯上**。查库先用 `ldconfig -p`（读的是 ld.so.cache，与实际链接行为一致），别按记忆里的目录去 `ls`。
- **模型型号 30B-A3B → 35B-A3B（错的被用户纠正）**：第一轮因为"Qwen3 官方 MoE 只有 30B-A3B 和 235B-A22B"，把用户说的"Qwen3.6 35B A3B"判定为"应该是 30B-A3B"。第二轮查 HF API 确认 **`Qwen/Qwen3.6-35B-A3B` 真实存在**（2657 likes，官方发布），而且是知识截止之后的新模型系列（还有 Qwen3.5-35B-A3B、Qwen3.6-27B）。→ 教训：**"我没听说过"不是"不存在"的证据**。涉及模型/版本这类快速变动的事实，查 API 再下结论，别用训练数据里的型号表去否定用户。
- **"完全没有恢复素材"（前提被推翻）**：SKILL.md 红线 5 原本基于"没有 DRIVE OS SDK 就没有任何镜像"。第二轮 `ls /opt/update/package` 发现板子**自带一整套 A/B OTA 原厂签名镜像**（Guest OS 根文件系统 4.4 GB + 签名 eMMC 镜像 1 GB + app.img 4 GB）。→ 这**不等于**可以刷机（仍缺 Aurix 串口 pinout 与 `bootburn.py`），但"没有任何恢复素材"这个前提不成立。已全量备份。
- **`strings` 检测 CUDA 符号（第一次全是假阴性）**：第一次用 `strings -a libcuda.so.1 | grep -qx <符号>` 检测，17 个符号**全报 no**，看起来像"驱动只支持 CUDA 11"。实际是 stderr 里刷了 17 行 `bash: strings: command not found`——板上根本没装 binutils。换 `grep -ac <符号> <文件>` 重测，**全部命中**，结论完全翻转。→ 教训：**批量探测时必须看 stderr，"全 no" 优先怀疑工具缺失而不是结论成立**；`command -v` 先探工具存在性再跑批量检测。
- **"llama-server 内存泄漏"（错，而且绕了一大圈）**：观察到每请求 RSS +123 MB、线性不收敛、`drop_caches` 不回收、PSS 同步涨，据此判定为泄漏。随后做了**四组对照实验**（带/不带 mmproj、ctx 32768/4096、CUDA/纯CPU、开/关 CUDA graph）——四组数字几乎完全一致，全部无果。最后查 `llama-server --help` 才发现 **`--cache-ram` 默认 8192 MiB**，它就是按这个上限在正常填 prompt cache 池；设成 1024 后第 12 轮涨满就完全平了。→ 教训：**遇到"内存持续增长"，先花 10 秒 `--help | grep -i cache` 查有没有配置上限，再怀疑泄漏。** 我把顺序做反了，代价是四组实验和一小时。
- **单次快照判断增长来源（方法学错误）**：看到 `nvmap` 客户端占 18.5 GiB 就断定"内存在 GPU 侧"。实际那是模型权重的正常常驻占用，与"增长"无关——去掉 UNIFIED_MEMORY 后 nvmap 恒定 18.54 GiB 而系统 used 照涨，才定位到常规内存。→ 教训：**判断"增长来自哪里"必须看差分，不能看快照。**
- **服务端全局关思考（判断错误，被用户当场推翻）**：为了解决"接客户端没反应"，我给 llama-server 设了全局 `--chat-template-kwargs '{"enable_thinking":false}'`。用户在 Cherry Studio 上立刻发现问题——**看不到思考链、思考强度调了没反应**，原话是"你说的这个思考被后端控制在这个最常用的软件都没法处理"。→ 教训：**服务端设全局默认会剥夺客户端的控制权**，而客户端的开关是用户唯一能直接操作的地方。正确解法是暴露 `-nothink` 模型名变体，让调用方自己选（用户的建议，比我原本设计的 `/v1-fast` 第二 base_url 更简单——客户端只认模型名，网关同步列表时自动带上）。另外我最初把"NewAPI 跑不通"也归因到思考模式，实际那次是我自己让服务挂了，两个问题被我混在一起，导致过度反应。
- **内存守护第三次成为故障源**：soft 阈值 1.8 GiB 时，WeKnora 的 RAG+ReAct 任务跑到一半被重启，`context deadline exceeded`。日志实证 `08:45:50 [memory-guard] available 1.56 GiB < soft 阈值，空闲重启`。根因是**把 `/slots` 空闲当成任务结束**——ReAct 是多轮调用，轮次之间必然有间隙，那一刻 slot 就是 idle 的。→ 已改：阈值降到 soft 0.35 / hard 0.2（用户要求"300mb 保个底别死机就行"，且 KV 预分配 + cacheRamMiB 封顶后内存本就有确定上界），并新增"5 分钟内有过推理请求就绝不重启"。教训：**自动化干预必须能区分"此刻空闲"和"任务结束"，前者不蕴含后者。**
- **内存守护阈值拍脑袋（自己造的坑）**：`softGiB` 直接设了 4.0，结果 embedding 服务一启动的正常波动就触发重启，还污染了一次内存测量（算出"embedding 净增 -6.73 G"这种荒谬数据，一度以为主模型崩了）。→ 教训：**自动化干预的阈值必须基于实测稳态水位来定，并且要有启动宽限期和连续多次确认**，否则守护本身会变成故障源。
- **`push.js` 整传丢执行位（紧接着上一条，同一天第二次自伤）**：把默认改成整传后，SFTP 按默认 umask 新建文件，`run-server.sh` 的 `+x` 没了，systemd 报 `203/EXEC Permission denied`，LLM 服务连续 9 次重启失败。我当时正在等"服务启动"，看到 120 秒还 down 才去查日志。→ 教训：**改传输逻辑时，权限位和内容一样是文件的一部分**；另外这次还差点误判成"新加的 `--reasoning-budget` 参数导致起不来"——失败原因要从日志读，不要从"我刚改了什么"猜。已改成传前记住远端权限、传完 chmod 回去。
- **`push.js` 默认断点续传损坏文件（我自己造的坑，代价是面板挂掉）**：昨天为传 16.5 GB 模型加了断点续传，判据只有文件大小。今天推改过的 `server.js` 时，它看到远端已有同名旧文件（大小不同），就从旧文件末尾偏移开始写，**结果前半段是旧内容、后半段是新内容的尾巴**，拼成语法错误的嵌合体，面板无限重启。更隐蔽的分支是大小恰好相等时直接 SKIP，一个字节没传却报 OK。本地 `node --check` 通过、板上 `SyntaxError`，这个组合就是传输损坏的特征。→ 教训：**`push` 的语义是"让远端等于本地"，续传是特例不是默认**。已改为默认整传 + 传完 stat 校验字节数，`--resume` 显式启用。**"本地测好的代码上板就崩"，先查传输环节，别急着怀疑代码。**
- **`GGML_CUDA_ENABLE_UNIFIED_MEMORY=1`（我自己加的，且假设错误）**：加它的理由是"Orin 统一内存，显存耗尽可回落"，还援引了 `concurrentManaged=0` 来支持"它导致泄漏"的猜想。实测去掉后 nvmap 稳定但泄漏依旧——**假设是错的**。不过这个变量本来也不该加：Orin 本就是统一内存，没有"回落"这回事。

## 【C 仍是推断 / 未验证】（转述必须带"推断/未测"）

- **~~3.9G 隐形内存~~ —— 2026-08-10 第二轮推翻，这条不成立了**：第一轮观察到 used 4.1 GiB、进程 PSS 只有 200 MB，据此判断"约 3.9 GiB 是内核级隐形预留，进程停光也拿不回"。第二轮同一台板子实测 **used 只有 1.25–1.33 GiB、MemAvailable 27.4 GiB**，那 3.9 GiB **自己回来了**。所以它不是常驻预留，而是某个时刻的瞬态占用（可能是 pkill 停栈后内核资源尚未回收，或大量文件 I/O 触发了回收）。**具体成因仍未查清**，但"拿不回来"这个结论是错的，别再引用。nvmap carveout 实测 `generic-0` = 1 GiB 且**全空闲**、`fsi` = 16 MiB、nvmap 客户端占用 0K——真正固定预留给 GPU 的只有这 1 GiB 出头。
- **fsi-carveout 是不是那 3.9G 的来源**：`/proc/device-tree/reserved-memory/fsi-carveout` 的 reg size = `0x100000000`（4GB），但其 base = `0x59e17f000000` 地址极高，**是否计入 Guest 的 MemTotal、是否等于隐形 used，未确证**。对话中一度怀疑是它，随即发现地址不在常规 DRAM 段（memory@80000000）而存疑。**结论：未定，别写成"3.9G 就是 fsi-carveout"。**
- ~~**稳态温度 73–77°C**~~、~~**散热是否够用**~~：**2026-08-12 用户加装风扇后实测解决，已移入 A 档，不再是未决项。**

- **CUDA 12.2 交叉编译 llama.cpp 能否编过**：`cuda-cross-aarch64-12-2` 包**存在**（NVIDIA repo 索引确认），llama.cpp 的 `ggml-cuda/CMakeLists.txt` 也**没有**硬性最低 CUDA 版本检查。但"包存在 + CMake 不拦"不等于"源码能编过"——`sm_87` 不在默认架构列表里、FlashAttention 的 mma 模板、CCCL 版本都可能出问题。**未验证**。
